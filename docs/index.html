The problem

One missing row of dashes

GFM requires a separator row under a table header. When a model omits it — which it does constantly — the whole table degrades into a paragraph of pipe characters. This is the single most common way an LLM report becomes unreadable.

✕ Strict CommonMark / GFM
| Model | MMLU | GSM8K |
| GPT-4o | 88.7 | 94.2 |
| Claude 3.5 Sonnet | 88.3 | 96.4 |
✓ Kintsugi

What it repairs

Built from a taxonomy of real mistakes

The recovery rules come from cataloguing how models actually break markdown, not from guessing. Each one is covered by fixtures drawn from that catalogue.

| | Tables

Missing separator rows, miscounted separators, ragged rows (merged into the column whose shape fits, never truncated), unicode and box-drawing pipes, glued tables, wrapped cells.

``` Code fences

Never closed, wrong closing character, short closers, closers carrying trailing text, and nested fences inside a ```markdown example.

** Emphasis

**bold that never closes — shut at the label colon or end of line, never spilling. Space-padded ** bold **, mismatched __bold**, crossed ranges.

∑ Math

$x$, $$…$$, \(x\), \[…\] and bare \begin{align} all survive intact instead of being chewed into emphasis and brackets.

• Lists

Unicode bullets, (1) / a) / i. markers, drifting indent widths, glued checkboxes, restarts, and commands left flush-left between steps.

⌁ Truncation

Documents that stop mid-fence, mid-table, mid-sentence. An unclosed fence ends where markdown structure plainly resumes rather than swallowing every section below.

</> Scaffolding

<thinking> blocks and control tokens like <|im_end|> are recognised, kept in the AST, and left out of the rendered page.

[^] Extensions

Footnotes, ==highlight==, GitHub alerts, :::note containers, definition lists — the syntax models reach for that CommonMark lacks.

↯ Linear time

Eleven adversarial constructs are parsed at 4× scale in CI and fail the build if cost grows superlinearly. Ordinary documents parse at roughly 8 MB/s.

The hard part

Knowing when not to help

Over-eager repair is what makes a tolerant parser worse than a strict one. If valid text gets "fixed", you can no longer trust anything it renders. Every heuristic is guarded, and the guards are tested as carefully as the repairs.

✓
a * b * c is arithmetic, not emphasis. So is 2 ** 3.
✓
$5 and $10 is money. $x^2$ is math.
✓
#1 priority and #!/bin/sh are not headings. ##Results is.
✓
*.py and **/*.ts are globs, left alone.
✓
One | in a sentence is not a table.
✓
A lone — Ada Lovelace is an attribution; a run of them is a list.
✓
Anything inside a code fence is never touched.
✓
Well-formed markdown yields zero repairs and the standard reading.
✕
Content is never deleted. Duplicated output keeps both copies.
✕
Whitespace alignment alone never becomes a table.

Usage

Two functions

Parse to an AST with a repair log, or go straight to HTML. Written in TypeScript, ships its own types, no runtime dependencies.

import { parse, render } from 'kintsugi-md';

// AST plus the list of repairs that were applied to get there
const { ast, diagnostics } = parse(source);

// or straight to HTML
const { html, diagnostics } = render(source);

for (const d of diagnostics) {
  // repair | note   ·   1-based line in the ORIGINAL source
  console.log(`${d.severity} L${d.line} ${d.code} — ${d.message}`);
}
